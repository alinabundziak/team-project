# Dev 1: Фінансові операції (Етап 2)

Усі фінансові ендпоінти доступні **тільки ADMIN**. MANAGER, TEACHER і PARENT отримують 403, без токена 401.
Помилки мають єдиний формат: `{ "error": { "status": 404, "message": "..." } }`.
Усі суми в JSON це **рядки з двома знаками після коми** (`"15000.00"`), щоб не втрачати точність.

## Ендпоінти

| Метод і шлях | Що робить | Вхідні дані |
|---|---|---|
| `GET /api/discounts` | Довідник знижок (0, 10, 20, 30%) | |
| `GET /api/tariffs` | Усі версії тарифів, `isCurrent` позначає чинну | |
| `PATCH /api/tariffs/:tariffId` | **Додає нову версію** тарифу (стару не змінює) | `amount`, `validFrom` (перше число місяця, `YYYY-MM-DD`) |
| `GET /api/children/:childId/tuition-estimate` | Розрахунок вартості навчання, нічого не записує | `period=MONTHLY\|ANNUAL`, `discountId` (необов'язково, для сценарію «а що, якби») |
| `GET /api/children/:childId/meal-estimate` | Розрахунок харчування, нічого не записує | `days` (1-31, необов'язково) |
| `POST /api/children/:childId/charges` | Створює нарахування за місяць (навчання + харчування) | `month` (`YYYY-MM`), `mealDays` (0-31, необов'язково) |
| `GET /api/children/:childId/charges` | Список нарахувань дитини | `page`, `limit` |
| `POST /api/children/:childId/payments` | Реєструє оплату (повну або часткову) | `amount` |
| `POST /api/children/:childId/refunds` | Повернення коштів по конкретній оплаті | `paymentId`, `amount`, `reason` (необов'язково) |
| `POST /api/children/:childId/adjustments` | Коригування нарахування | `chargeId`, `direction` (`INCREASE`\|`DECREASE`), `amount`, `reason` |
| `GET /api/children/:childId/balance` | Поточний баланс і борг | |
| `GET /api/children/:childId/financial-history` | Усі операції дитини від нових до старих | |

Відповідь `balance`: `charged`, `adjustmentsIncrease`, `adjustmentsDecrease`, `paid`, `refunded`, `debt`, `overpayment`.
Подія в `financial-history`: `type` (`CHARGE`, `PAYMENT`, `REFUND`, `ADJUSTMENT`), `id`, `date`, `amount`, `details`.
У `details` нарахування лежать тариф і знижка, застосовані на момент створення.

## Формули

- Навчання за місяць: `T_m = тариф × (1 − d)`, де d це знижка (0, 10, 20 або 30%).
- Навчання за рік (лише в `tuition-estimate`): `T_y = тариф × 12 × (1 − d) × 0,88`. Приклад: пільга 20% дає 126 720 грн.
- Харчування за день: `M(a) = 300 + 100 × (a − 2)`, де a це вік 2-5 років (300, 400, 500, 600 грн).
- Сума нарахування: `T + ціна за день × кількість днів`.
- Борг: `D = нарахування + коригування(+) − коригування(−) − оплати + повернення`. Якщо результат від'ємний, борг дорівнює 0, а різниця показується в `overpayment`.

## Таблиці БД

| Таблиця | Що зберігає |
|---|---|
| `charges` | Нарахування за місяць: тариф, знижка, ціна харчування і дні **на момент створення**, суми |
| `payments` | Оплати дитини (сума, час) |
| `refunds` | Повернення, прив'язані до конкретної оплати (причина необов'язкова) |
| `adjustments` | Коригування, прив'язані до нарахування: напрям, сума, **причина і автор обов'язкові** |
| `tariffs` | Версії тарифів: `code`, `amount`, `valid_from` |
| `meal_rates` | Версії цін харчування: вік, ціна за день, `valid_from` |
| `discounts` | Знижки 0, 10, 20, 30% (використовується `children.discount_id`) |

## Ключові рішення

1. **Нарахування це знімок.** Воно зберігає власні значення тарифу, знижки та ціни харчування. Через API його не можна змінити чи видалити, тому зміна тарифу, знижки чи ціни не перераховує старі нарахування.
2. **Тарифи версійні.** `PATCH /api/tariffs/:id` створює новий рядок. Нова версія починається з 1 числа місяця, не в минулому і пізніше за останню наявну. Нове нарахування бере версію, чинну на 1 число його місяця.
3. **Ціни харчування теж версійні.** Для кожного віку діє одна ціна, нова версія додається рядком із пізнішим `valid_from`. Версії додаються в БД, окремого API для цього немає.
4. **Знижка** береться з `children.discount_id`; якщо його немає, то 0%. Підтримуються лише 0, 10, 20, 30%, інакше 409. На харчування знижки не діють.
5. **Харчування.** Без `mealDays` береться стандартний місяць у 20 днів. `mealDays: 0` означає нарахування лише за навчання (потрібно для дітей поза віком 2-5). Вік рахується на 1 число місяця нарахування.
6. **Одне нарахування на дитину за місяць.** Повторне створення дає 409.
7. **Оплата не прив'язується до конкретного нарахування**, вона зменшує загальний борг дитини. Часткова оплата це оплата менша за борг. Переплату дозволено.
8. **Повернення** прив'язане до оплати цієї дитини і не може перевищувати суму оплати мінус уже повернене (інакше 409). Повернення збільшує борг. Якщо зобов'язання вже не чинне, потрібне коригування `DECREASE`.
9. **Коригування** прив'язане до нарахування цієї дитини. Автор береться з токена, причина обов'язкова. `DECREASE` не може перевищувати чинну суму цього нарахування (нарахування плюс збільшення мінус зменшення), інакше 409.
10. **Історія незмінна.** Нарахування, оплати, повернення і коригування лише створюються. Усі зв'язки мають `onDelete: Restrict`, тому дитину з фінансовими записами видалити не можна (409).

## Початкові дані

Після `npm run db:generate` запустити один раз:

- `node scripts/seed-discounts.js`: знижки 0, 10, 20, 30%.
- `node scripts/seed-tariffs.js`: тариф навчання 15 000 грн з 2026-09-01.
- `node scripts/seed-meal-rates.js`: ціни харчування 300, 400, 500, 600 грн з 2026-09-01.

Нарахування за місяць до 2026-09 повертає 409, бо немає чинного тарифу.
Скрипти можна запускати повторно, наявні записи вони не змінюють.

## Для продовження роботи (звіти)

- Брати суми з `balance` і `financial-history`, а не рахувати самостійно.
- Нарахування (`CHARGE`), надходження (`PAYMENT`), повернення (`REFUND`) і коригування (`ADJUSTMENT`) це окремі типи подій.
- У таблиці `payments` є лише `created_at` без окремої дати оплати, якщо потрібно це можна змінити.

## Обмеження та відкриті питання

- Річна оплата рахується лише в `tuition-estimate`, нарахування створюються помісячно.
- PARENT не бачить фінанси (403). Доступ власних даних можна додати після погодження.
- Нові версії цін харчування додаються в БД вручну.
